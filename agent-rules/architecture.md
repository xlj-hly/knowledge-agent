# 架构与边界

适用：新增业务模块或跨模块流程，改变模块依赖、身份上下文、共享状态或事务边界。

### ARCH-001：先明确本次设计

- 编码前查找现有入口和同类实现，说明本次职责划分、依赖方向、数据流、关键状态所有者、失败路径和验证方式，再开始实现。
- 设计说明的详细程度与变更风险相称；局部改动可以简述，不机械新建架构文档。已有设计可引用，边界变化时同步更新。

### ARCH-002：按职责组织依赖

- 入口负责组装与调用，各能力明确维护归属。Go 按 [GO-011](../server/AGENTS.md) 的领域、应用、基础设施与接入四层组织，各层内部按业务能力内聚；前端以完整页面为主要实现入口，页面私有实现就近放置，公共 API、状态与组件按职责组织，不机械套用服务端的业务目录。
- 文件落位与跨模块引用按 [目录与依赖](directories.md) 及所属模块的目录规则执行。
- HTTP、页面与平台 API 作为适配边界；可独立验证的业务规则与流程不依赖 HTTP 上下文、组件实例或具体页面。
- 已明确持续扩展的项目，从首版落实应用组装、业务用例与外部能力的依赖边界；不能以当前功能较少为由延后必要分层。新增模块通过公开能力契约接入，不能依赖另一模块的内部持久化实现；尚未实现的功能不预建空模块。
- 独立职责可以因隔离变化、状态或测试而提取；公共抽象需要实际共性。职责分离不以复用次数、文件行数或目录层数作为唯一依据。
- 可配置外部服务扩展到多个供应商时，将预设、连接字段、能力校验与实际适配关联到显式注册目录；页面消费目录，业务依赖统一能力接口，避免领域、页面和调用实现分别维护品牌名单与字段分支。连接字段须明确类型、敏感输入、默认值与引用后不可变属性；配置按提交值完整替换，不隐式继承旧凭据，空值按字段必填规则校验。已授权配置接口可按契约回显凭据，敏感字段元数据用于输入展示及默认值约束，不自动过滤响应；凭据不得写入静态包、未授权接口或日志。同协议供应商复用驱动，专用差异归其适配模块；未实现驱动不得仅添加预设冒充支持。注册实例由组装层创建并明确注入，不依赖可变全局注册或隐式初始化副作用。
- Prompt、参数方案等纯数据预设按其所属能力独立维护和显式组装；可选项名称、说明及默认值由相应目录提供给页面，避免多处复制。预设引用的执行策略须与实际实现一致；参数方案、业务枚举和协议驱动各自承担职责，不为统一外观建立万能插件框架。

### ARCH-003：明确身份、状态和事务所有权

- 为共享状态、会话、表单草稿和持久化写入明确所属的用户或租户，以及创建、更新、失效和清理责任；避免多个模块各自维护互不一致的状态副本。
- 身份或租户变化时，同时处理旧请求、缓存、表单和授权视图；恢复新身份不能继续使用旧身份的数据。前端展示权限不能代替服务端授权。
- 多步写入按业务不变量确定事务边界，业务成功以后端确认及持久化结果为准；客户端取消等待不能作为写入已回滚的依据。

### ARCH-004：明确跨边界契约

- 明确输入、输出、错误类别及缺省、`null`、空值的语义，按需区分完整替换与部分更新；无效数据不得静默转为业务默认值。
- 认证失败、权限不足、业务冲突与依赖故障保留不同语义，调用方据此决定重试、提示或失效处理。
- 契约变化同步受影响的服务端、客户端和测试；数据库记录、内部状态不直接作为允许客户端写入的字段集合。
