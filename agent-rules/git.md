# Git 提交规范

适用：准备 Git 提交、编写提交信息或整理提交范围与历史。

### GIT-001：使用 Conventional Commits

- 遵循 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/)，格式为 `<type>(<scope>): <description>`；没有合适范围时可省略括号及 scope。
- type 使用小写英文：`feat` 新功能、`fix` 缺陷修复、`refactor` 不改变外部行为的重构、`docs` 文档、`test` 测试、`perf` 性能、`build` 构建与依赖、`ci` 持续集成、`style` 仅格式、`chore` 其他维护、`revert` 撤销提交。不要用 `style` 表示有实际界面行为变化的功能。
- scope 使用实际模块或业务能力的小写名称，例如 `saas`、`server`、`web`、`uniapp`、`storage`、`db`、`conventions`；不使用文件列表作为 scope。
- description 默认使用中文，简洁说明具体改变，结尾不加句号，避免“更新”“修复问题”等无明确含义的标题。正文按需说明原因、兼容影响和实际验证结果，标题与正文之间留空行。
- 不兼容变更在 type/scope 后加 `!`，并在正文使用 `BREAKING CHANGE:` 说明影响及迁移方式；提交确有对应问题单时再附引用。

```text
feat(saas): 支持按企业域名识别租户
fix(storage): 正确取消对象读取
docs(conventions): 约定提交格式与验证要求
```

### GIT-002：保持提交完整且范围明确

- 一个提交表达一个可独立说明的改动，包含必要的代码、测试、配置示例和文档；共同完成同一业务目标的跨模块修改可放在同一提交。独立的规范整理与业务功能优先分开提交，不机械按文件拆分。
- 提交前检查工作区和已有暂存内容，明确本次文件范围并按路径暂存；保留其他任务和用户的改动及暂存状态，不使用无范围的 `git add .` / `git add -A` 混入无关内容。
- 不提交真实凭据、`.env` 本地配置、运行数据、日志、测试报告、依赖目录、构建产物或本地执行记录；配置示例只包含占位值。依赖变更提交对应锁文件。
- 独立参考仓库不直接作为嵌套 Git 仓库加入主项目；需要子模块或引入第三方源码时，先明确其维护方式、版本与许可证。

### GIT-003：验证暂存结果并按授权操作

- 按 [测试规范](testing.md) 执行与改动相关的检查，核对入口、测试发现范围和实际结果；相关检查失败时先处理，不绕过有效检查。外部集成的跳过或未执行必须明确说明。
- 提交前检查 `git diff --cached --stat`、暂存差异和 `git diff --cached --check`，确认没有遗漏关联文件、敏感值或意外删除；提交后检查提交记录和剩余工作区状态。
- 只有用户授权提交时才创建提交；授权本地提交不等于授权推送、发布或改写历史。未经明确要求，不执行 amend、rebase、强制推送或跳过提交钩子。
