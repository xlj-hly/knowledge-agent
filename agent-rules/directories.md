# 目录与依赖

适用：新增、移动、拆分或重命名源码与测试文件，调整目录或模块引用。

### DIR-001：按所属模块的组织方式落位

- Go 按 [GO-011](../server/AGENTS.md) 组织业务能力；React 与 uniapp 按 [WEB-007](../react-app/AGENTS.md)、[UNI-007](../uniapp/AGENTS.md) 采用页面优先结构，页面专属实现就近放置，API、跨页面状态和公共组件按职责集中。
- 目录树表达职责归属，按实际实现创建文件和子目录；小功能在所属页面或模块内平铺，不预建空壳或为单个函数增加多层目录。
- 根 `db/` 保存数据库结构 SQL 与结构说明，`docs/` 保存项目设计与接口说明，`agent-rules/` 保存开发规则；模块专属运行配置放所属模块根目录。
- `server`、`react-app`、`uniapp` 是各自构建与发布的模块；客户端不跨根目录相对引用另一个客户端的内部源码。确有共享源码需求时，先明确独立包的契约和构建边界。

### DIR-002：保持模块入口与依赖单向

- 模块之间通过明确公开的用例、类型或组件协作，不跨入另一模块的私有存储、组件、Hook 或状态实现。前端页面私有代码由该页面使用，API、Store 和公共能力不反向依赖具体页面或应用入口。
- 确需提取独立前端业务模块时，从明确契约文件或入口组件导入；只有需要集中公开接口时才增加 `index` 等出口，并使用有限的显式导出。出口不能把整个内部目录重新导出。
- 跨模块依赖保持单向。双向调用由上层组合或调整业务归属解决；仅改成从 `index` 导入不算消除循环。

### DIR-003：共享能力有明确范围

- 页面专属组件、校验、样式和交互状态留在页面旁，接口类型靠近所属 API；Go 数据访问归所属业务。多个调用方不等于通用能力，共享概念明确单一维护位置，避免复制同义类型和规则。
- 区分基础技术能力与应用公共能力：基础函数和 UI 不依赖具体页面或业务流程；应用公共组件可表达品牌、身份摘要等展示语义，公共请求可统一配置本项目的认证与租户策略。两者都不反向依赖具体页面或应用入口。
- 按明确用途命名，如 `request`、`date`、`storage`；不持续向 `utils`、`common`、全局 `types` 或万能 `service` 文件追加不相关职责。

### DIR-004：测试与资源靠近消费方

- Go 局部测试随被测包放置；前端单元、组件与 Hook 测试默认靠近被测实现。跨模块集成测试、产品 E2E 及其启动辅助放模块专用测试目录，具体位置见模块规范。
- fixture 和测试辅助归消费它的套件所有；确有多个套件复用时再提取到模块 `tests/fixtures`、`tests/helpers`。不将测试依赖、凭据或 fixture 放入客户端公开静态资源目录。
- 业务样式和导入资源靠近所属业务或组件，公共样式与资源按模块规范放置；测试结果、构建产物和本地运行数据不作为业务源码维护。

### DIR-005：按任务渐进调整并验证真实入口

- 新增独立模块按目标结构落位；局部修复不附带全量搬迁。拆分已有职责时同步迁移直接相关调用方，避免建立与存量同义的第二套 `api`、`services` 或公共组件目录。
- 移动后同步 import、路由与页面注册、静态路径、工具配置、测试发现范围及相关文档；路径别名必须由实际构建和测试工具支持。
- 核对启动入口与测试实际使用迁移后的实现，清理本次移动遗留的失效引用和旧实现。确需暂时兼容时，旧入口只做转发，不保留两套业务逻辑。
